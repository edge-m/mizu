# Mizu / Hono benchmark results

Measured 2026-09-26 on the local checkout.

## Environment

- Runtime: Node.js `v22.22.2`, x64 Linux
- OS/kernel: Ubuntu Linux, `7.0.0-34-generic`
- CPU: AMD Ryzen 7 7735HS, 16 logical CPUs
- Mizu: `0.1.0`, commit `1a2a23de4fbaf2c9f401d6cec460f41ae652ccaa`
- Hono: `4.13.9` (repository benchmark reference HEAD `90d02fb1645c12a65d27f39594d2129db2065ba7`)
- HTTP tool: bombardier built from `github.com/codesenberg/bombardier@master` during this run

## Framework overhead (`fetch(Request)`)

Command:

```sh
npm run bench:fetch:compare
```

Three fresh-process rounds were run, alternating framework order. Values below are mitata `p50` in nanoseconds per operation; ratio is Mizu/Hono, so lower is better.

| Case | Mizu p50 | Hono p50 | Mizu/Hono | Mizu raw p50 | Hono raw p50 |
| --- | ---: | ---: | ---: | --- | --- |
| GET `/` | 7,820 | 5,417 | 1.44x | 7,435 / 7,820 / 7,870 | 5,189 / 5,417 / 5,427 |
| JSON `/user` | 9,256 | 6,857 | 1.35x | 9,247 / 9,256 / 9,410 | 6,607 / 6,857 / 7,046 |
| path/query | 11,187 | 8,231 | 1.36x | 11,246 / 11,163 / 11,187 | 8,079 / 8,384 / 8,231 |
| multiple routes | 10,712 | 7,430 | 1.44x | 10,796 / 10,529 / 10,712 | 7,184 / 7,458 / 7,430 |
| POST JSON body | 21,537 | 15,578 | 1.38x | 21,938 / 20,991 / 21,537 | 15,578 / 15,531 / 15,644 |
| one middleware | 8,376 | 6,043 | 1.39x | 8,175 / 8,376 / 8,560 | 5,926 / 6,043 / 6,094 |

The three-round spread was modest for most cases. The largest observed raw range was the Mizu POST JSON case (about 4.5% from minimum to maximum); Hono's values were generally within about 5%.

## HTTP benchmark

Command:

```sh
BOMBARDIER=/tmp/mizu-bench-bin/bombardier npm run bench:http -- --runs=2 --duration=3 --concurrency=500
```

This is a shortened local run (2 runs × 3 seconds) to keep the measurement practical; the default runner remains 3 runs × 10 seconds, matching Hono's default duration and concurrency. Values are averages across the two runs. Ratio is Hono/Mizu req/sec, so higher is better; latency ratio is Mizu/Hono, so lower is better.

| Case | Mizu req/s | Hono req/s | Hono/Mizu | Mizu latency | Hono latency | latency Mizu/Hono |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GET `/` | 8,893 | 34,198 | 3.85x | 56.19ms | 14.55ms | 3.86x |
| JSON `/user` | 10,418 | 33,495 | 3.22x | 47.72ms | 14.85ms | 3.21x |
| path/query | 9,737 | 30,879 | 3.17x | 51.06ms | 16.15ms | 3.16x |
| multiple routes | 9,756 | 33,857 | 3.47x | 50.79ms | 14.67ms | 3.46x |
| one middleware | 10,398 | 33,029 | 3.18x | 47.76ms | 15.06ms | 3.17x |
| POST JSON body | 7,605 | 25,115 | 3.30x | 65.36ms | 19.80ms | 3.30x |

- GET `/`: Mizu `8,888 / 8,898`; Hono `34,602 / 33,795`
- JSON `/user`: Mizu `10,569 / 10,268`; Hono `33,717 / 33,272`
- path/query: Mizu `9,683 / 9,791`; Hono `31,696 / 30,062`

## Analysis

The direct framework-overhead gap is approximately 1.29–1.42x in these cases, while the HTTP gap is approximately 3.17–3.85x. That larger HTTP difference should not be attributed to routing alone.

The implementation inspection found a likely contributing boundary: Mizu's current Node adapter creates a Web `Response` and streams it through `Readable.fromWeb(...).pipe(response)`, while the installed Hono Node adapter has fast response paths that write small string/byte bodies directly with `response.end()` and set `Content-Length`. Thus the HTTP numbers include materially different adapter response paths, as intended by an end-to-end benchmark, whereas the fetch benchmark isolates the framework more closely. No Mizu production code was changed to tune this benchmark.

These are machine-local results. The short HTTP run and high concurrency are useful for comparison, not a universal deployment ranking; rerun with the documented default duration before using the numbers for release decisions.
